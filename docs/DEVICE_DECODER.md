# Device decoder ownership and diagnostics

Each Android viewer attempt owns exactly one decoder process. Reconnection, cancellation, startup failure, and normal scope exit kill and reap that exact child when necessary. Child waits and stderr-reader joins happen outside the shared decoder-slot mutex. An old attempt cannot stop a successor or publish a late frame. Cancellation is checked before spawning and again before admission.

A connected socket is not evidence of a live decoder. The Android consumer reports `decoder: true` only after a valid decoded JPEG has been written to its owned frame slot. A failed decoder disables input, clears that flag, and returns `device_decoder_failed`; it does not silently switch to screenshots or repeat the same local decoder failure. The existing screenshot mode remains distinct and is used only when the decoder executable is absent. No codec-thread flags were changed: the exact existing command successfully decoded a retained synthetic stream, so the emulator failure's cause remained unproven.

For private acceptance inside `android-sandbox`, explicitly set `OMARCHY_T3_DEVICE_DIAGNOSTICS_DIR` on the contained CLI to an existing private directory owned by its user with mode 0700. This is optional instrumentation, not a replacement for runtime behavior. All path components reject symbolic links. Every output uses a new exclusive 0600 regular-file slot; no diagnostic cleanup traverses or deletes a tree. Invalid or exhausted requested instrumentation fails visibly instead of silently pretending evidence was captured.

Each attempt can retain at most 1 MiB of accepted H.264, 1 MiB of length-prefixed original binary packets, 64 metadata/text events, and the final 8 KiB of decoder stderr. A CLI process admits at most 16 instrumented attempts. Reports distinguish an owner-requested stop from a natural process exit and report capture write failures. Text summaries keep only allowlisted type, codec, dimension, orientation, status and error-code fields; bearer credentials, ticket URLs and arbitrary messages are not copied. Header hex and event order preserve the framing sequence. A separate terminal field records the WebSocket close code or a categorical read failure even after the event budget is exhausted. Only known nonsecret close reasons are retained; arbitrary reasons are represented by their byte length. Any terminated transport disables input and decoder flags. The original media can contain displayed content, so this opt-in evidence is private and intentionally retained.

`tools/test-device-decoder-container` compiles only the decoder integration target and the reviewed main-binary flow filter. It freezes executables and native libraries under the shared build lock before running them in private rootless Podman with read-only sources, private HOME and retained fixtures, and no network. It does not clear or bypass the full-runtime audit marker. Physical tests cover reaping, cancellation admission, stale-attempt fencing, unlocked process waits, bounded diagnostics, permissions, and refusal of a link whose target stays within its own fixture. Real SDK HTTP/WebSocket flow tests verify both an explicitly failing codec and a real synthetic H.264 decoder, including emitted surface flags and an actual JPEG frame. The producer's thread bound controls only the synthetic fixture generator; decoder arguments remain unchanged.

These tests establish process ownership, truthful state and observability. They do not establish live Android emulator video parity. Phase 10 opened the actual human device session with agent access disabled, but failed before its first decoded image; the old consumer had discarded its stderr and encoded data. That run shut down gracefully with zero prohibited recursive-removal or helper-build attempts. A later real run must retain codec evidence and prove nonblack Settings-to-Home frames and viewer closure before acceptance.

The actual Node `expo-device-hub` CLI uses `middleware.createRouter` and defaults to `grpc-screenshot`. Its `attachEmuSocket` catches a failed `router.ensure` and closes the socket without a code or reason. The standalone `startServer` is a different transport entry point. Whole-native no-VM probes cover both paths and demonstrate that the allowed device `/api` HTTP request returns the original capture-start error as HTTP 503, whereas the Node WebSocket path erases it. A startup-only diagnostic must use that HTTP path with fresh media access before opening a viewer; a healthy 200 response must report streaming state and real dimensions. No real emulator capture has been accepted on the basis of those synthetic probes.
