# Native settings scopes

Reference: native checkout `5a4e9980533705774dc3f45b35cacf76c3d78dbc`, `components/settings/{settingsScope,scopedSettings,useScopedSettings}.ts`, `packages/shared/src/projectSettings.ts`, and `packages/contracts/src/{settings,t3ProjectFile}.ts`.

`src/scoped_settings.rs` handles `settings` operations carrying an explicit `scope.targets` list. Each target is an environment and nullable native project ID. There is no wildcard mutation in the transport: the UI resolves All environments / project / checkout to exact targets before dispatch. Unknown environments, malformed/empty/mixed target kinds and duplicates fail validation. Each project is checked against the current native shell snapshot; a removed selection is never replaced by an environment-wide target.

The UI reuses `ProjectModel.js` repository grouping and the same field/model controls as General and the composer. Projects now has a partial settings page, and sidebar project-settings actions open it without changing chats. Physical project actions retain the clicked environment and checkout even when another chat is selected. Environment-only pages narrow back to one environment.

Reads use native `server.getConfig`, `server.getSettings`, `/api/auth/session` and the existing shell projection. Project settings are gated by the native `projectSettingsOverrides` capability; permissions are gated by the current session's `settings:write`. Optional `projects.readFile` reads only that project's `t3.json`, using the authoritative workspace root. No raw credentials, settings document, file contents, or provider configuration is returned to QML.

Resolution follows project override → environment → file → built-in for the two native file-backed keys. Legacy model/workspace fields apply only before `projectSettingsFolded`. A nullable model override remains Automatic; removing an override means inherit. Disabled-provider defaults fall back. JSONC comments/trailing commas are accepted, and invalid/truncated/missing project files are absent. The file decoder validates the known native fields and script shapes but is a targeted Rust adapter, not execution of Effect's TypeScript decoder.

Writes use `server.updateSettings` with the native patch schema and read back fresh settings. A project entry is replaced as native specifies: unrelated keys in that entry are preserved, partial object values are completed from its effective settings, and explicit reset removes the whole native setting key. Provider/model choices are checked against each environment's catalog, including project-enabled providers. Model options remain typed. There is no automatic write retry or file edit.

Fields expose native source, explicit override, writable and mixed-value metadata. Multi-target writes report each successful and failed target; they are not an atomic transaction. A target without settings permission is never written, and a failure does not hide successful targets. Older-server dropped writes are detected using the same recursive unchanged-value rule as native. Partial failures retain staged text edits, show saved-target counts and require a refresh before further editing. Request correlation discards replaced or duplicate results.

Verification: five Rust tests cover precedence, folded/legacy settings, nullable values, entry preservation, nested patches, JSONC/data safety, mixed values, exact native HTTP/Effect RPC writes/readback, and partial success with a read-only environment. Serialized QML tests `preferences-scope` and `project-preferences` cover exact axes, inherited reset, environment-only row disabling, stale checkout handling and cross-chat remote settings entry. Existing preferences/design/defaults and project menu tests are also exercised.

Remaining differences: this UI scopes the currently implemented server fields; it does not make omitted settings controls implemented. Native per-key inheritance-chain popovers with project-override enumeration, complete project-management/scripts/cleanup sections, all client-local preference controls and native search-result navigation remain pending. Provider setup/authentication remains a separate incomplete page. Existing one-time worktree approval stays in the new-thread flow.
