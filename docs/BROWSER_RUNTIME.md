# Native browser workspace and Qt runtime

The worktree now has a **native QML browser workspace mounted in the chat panel**, backed by an isolated Qt website renderer and native T3 metadata/actions. The current uncommitted live-import and localization changes have not been installed. It does not establish complete browser or application-screen parity: server streaming/automation, complete menu/device/history/recording flows and packaging remain pending; live import still differs in completion latency from the original. Preserve the separate HTML document renderer and the whole application QML/Quickshell UI.

## Original contract and boundaries

Reference: T3 Code `5a4e9980533705774dc3f45b35cacf76c3d78dbc`. `apps/desktop/src/ipc/methods/preview.ts:resolvePartitionScope` gives Default the bare environment ID; other profiles use a JSON tuple `[environmentId,profileId]` in a distinct namespace. `BrowserSession.ts:getPartition` hashes the scope with SHA256 and uses the first20hex characters, persistent/ephemeral prefixes and the profile marker. `browser_runtime.rs:partition` ports that identity for supported, well-formed Unicode strings, using the existing native profile-ID validator. It does not share or reinterpret Electron database files.

One Qt process owns one environment/profile partition and multiple tabs. The profile manager now coordinates local Qt and native server cleanup. After fresh scope/role preflight and consuming the confirmation view, it reserves the exact environment/profile pairs, revokes local input grants, hides stale frames, flushes/reaps each owned Qt process, and clears only its derived Qt storage directory under an exclusive OS lock. The reservation spans server acknowledgements and metadata CAS. Other profiles/environments remain running. Cold profiles are cleared even when they have no process this session. Server cleanup still calls only native `preview.clearProfile`; local-only environments can clear their own Qt data without server `preview:operate` permission.

This follows original `IntegrationsSettings.tsx:clearBrowserProfileData`, `BrowserSession.ts:clearCookies/clearCache` and `preview.ts:resolveClearPartitions`. Electron clears cookies/localStorage/IndexedDB/service workers and cache; Qt6.11 has no matching public aggregate site-storage API, so O3 stops the profile and removes its entire owned Qt engine directory, including engine bookkeeping. It never deletes or imports Electron storage. Profile metadata/default removal waits for every applicable local/server acknowledgement; failures or uncertain flush/deletion/RPC outcomes retain metadata and never automatically replay. The OS lock is outside the erasable partition, verifies the held inode against the derived partition identity, and blocks another O3 renderer from reopening during cleanup. This is not cross-client coordination with Electron's distinct profile data.

Persistent Qt data lives under native T3 userdata/ot3-browser-profiles, outside Electron and the document sandbox. Incognito uses an off-the-record WebEngineProfile, memory cache and no persistent cookies/storage path. Rust derives paths, creates private0700 directories, rejects symlink leaf directories and validates initial size/zoom against the generated native contract. Unrecognized initial payload fields are discarded. Private0600 frame PNGs live in disposable owned cache directories and are atomically replaced; normal renderer exit removes them.

The renderer entry point forces offscreen/software Qt and DPR1, with a separate GUI application/bootstrap library. Neither Quickshell nor the normal Rust worker loads WebEngine. There is no WebChannel/native object, Node or T3 credential in the page's JavaScript context. T3 transport and authorization belong to the Rust session coordinator outside this process. Its child environment is allowlisted and does not forward backend/agent secrets.

## Private renderer protocol

`browser-render` takes a bounded64KiB length-prefixed JSON bootstrap on stdin, then bounded newline-delimited commands. `ui/browser/browser-host.cpp` provides the Qt application, one QQuickWebEngineProfile, private frame capture, input and cookie-write acknowledgement. `T3BrowserSurface.qml` owns the tabs, identified by unambiguous JSON tuples of thread/tab IDs. Initial dimensions honor the native240..3840/maximum-area limits; resize also bounds allocation. Zoom defaults use the native ladder; the low-level view supports per-tab adjustment. Native appearance emulation remains pending; do not substitute forced recoloring for prefers-color-scheme.

Current commands include open/activate/navigate/back/forward/refresh/close-tab, resize/zoom, pointer/wheel/key input, evaluate, import-cookie and close. Outputs include ready/frame, navigation status and history flags, tab closure, evaluation, cookie acknowledgement and requests for context menu/file selection/new window/external protocol. Evaluation is a private trusted-controller primitive, **not an authorized public automation API**. The current coordinator validates ownership, scope and permissions for native UI controls; the full desktop automation broker remains pending.

Only HTTP(S) and about:blank are admitted as direct navigation here. Custom schemes generate a request for later user confirmation and never launch the OS. Native NEVER_EXTERNAL_PROTOCOLS prevents local/script/internal schemes from becoming prompts. File selection, context menus and popup requests are surfaced but their UI handlers remain pending. Downloads, recording/input overlays, native dialogs, passkeys, favicon handling, viewport/device emulation and the rest of the original desktop bridge still require implementation/verification. These limitations do not constitute complete parity.

Capture is render-driven, bounded to roughly30fps and suppresses its own repaint loop. Idle pages do not continuously capture. This is the same architectural need as the existing document guest, but a distinct implementation/profile policy; the document host/sandbox was not changed.

## Cookie import target

The private import-cookie command writes to the fixed process/profile via QWebEngineCookieStore. It handles URL/name/value/domain/path, expiry, secure/httpOnly and sameSite metadata, one cookie at a time. Success is acknowledged only after observing the expected cookie added; missing acknowledgement is uncertain and is never automatically retried. Invalid URL/size/expiry is rejected, concurrent imports are refused, and cookie values are never echoed in acknowledgement events. This is the **destination half only**: no source browser cookies, credential store or existing profile were read. Source discovery and Linux cookie readers now exist in Rust (see below); the original wizard, complete target orchestration and native registration-after-success remain pending.

### Metadata transport connected to native state

`src/preview_transport.rs` reads `preview.list` and subscribes to `subscribePreviewEvents` through the existing authenticated `t3-protocol` connection, including its normal bearer/DPoP routing. It checks the native `orchestration:read` role and projects `canOperate` separately; this path never opens a tab, launches a renderer, reports profiles/status or modifies metadata. Output whitelists bounded native session/event fields, preserves desktop/server runtime and profile/reveal/automation-owner identity, validates legacy viewport presets and native zoom values, and drops unknown config/auth fields. Event snapshot thread/tab identity must match its envelope; lists must belong to the requested thread and contain unique tabs. UTF16 string limits and JavaScript integral-number semantics are respected.

The subscription starts before its first list read. A quiet stream's first idle tick also obtains a list. Since the original stream has no explicit subscription-ready acknowledgement, a bounded five-second list refresh repairs startup/reconnect gaps; an event with another epoch requests a fresh list immediately. The original reducers, rather than callback timing, resolve event/list ordering. This polling is an O3 reconciliation adaptation, not a claim that the original web client polls every five seconds. Cancel is checked before emissions; native websocket heartbeats/interrupts are retained.

`src/preview_watch.rs` owns one cancellable visible subscription with generation checks and bounded reconnect backoff. `preview-watch` is admitted only while the main native panel is visible. Hide, clear-selection, changed selected thread and worker disposal cancel it. `preview-read <environment> <thread>` is an explicit read-only CLI route. Neither path grants browser automation.

`ui/js/PreviewSessions.js` and `T3Backend.qml` connect receipts to the generated native state store. The future native panel activates `previewVisible` (false by default). Request nonces bind environment/thread and worker lifetime; a list establishes an origin, events cannot establish one, and store caches are scoped by environment/origin so even identical epochs cannot mix two server origins. Disconnect retains readable state while marking it disconnected and disabling operation permission. The main panel now mounts the native workspace described below; no installed plugin was changed.

### Native lifecycle actions connected to the bridge

`src/preview_actions.rs` implements exact native payloads for `preview.open/navigate/resize/adjust/refresh/close`. Input is whitelisted, native URL normalization is left to T3, and provider ownership/reveal fields are not accepted from human controls. Fresh auth must include read and `preview:operate`; the selected origin and server epoch must still match, the target tab must still exist, and server-runtime opens require `serverBrowser`. Snapshot replies must match the captured thread/tab. Refresh and close have void native success contracts; they do not return a snapshot. In particular, desktop refresh needs the local guest coordinator (now provided by `browser_sessions.rs`): the native manager intentionally emits no refresh event.

`src/preview_command.rs` serializes accepted actions per environment/thread, independently across keys, with bounded admission (32 active/idle keys, 32 queued commands per key). Idle queues retire after60seconds using a shared retirement/admission gate so an accepted command cannot disappear at that boundary. Accepted actions can finish after thread navigation; the receipt remains bound to its original scope. Hide rejects new actions. A preflight failure is known; any failure or invalid reply after dispatch is uncertain, with no automatic retry and no raw server error body sent to QML. Within this worker lifetime, up to4096 dispatched request IDs are retained without eviction to reject replay. There is currently **no durable command journal across a complete worker restart**, and exhausting that admission limit requires a later lifecycle/journal solution; do not claim unlimited native parity yet.

`PreviewSessions.js` exposes these actions through `T3Backend.previewAction`, captures scope/default identity against caller overrides, uses original optimistic-close/rollback reducers and preserves active focus for background mutations. Operations survive selection changes in their captured scope. Unknown outcomes block more commands in that scope until explicit acknowledgement requests a fresh read (never resends the mutation). For uncertain closes, acknowledgement removes suppression without restoring an old snapshot, allowing the fresh authoritative list to decide whether a tab still exists. Worker loss marks pending outcomes uncertain and discards replayable commands. This is session-only frontend state, not a durable restart journal.

### Owned Qt guest pool and native page item

`src/browser_guest.rs` now supplies the lower-level guest pool for that integration. It is connected to the authorized coordinator described below; it is mounted through the native QML workspace in the worktree, **not installed**. Server-runtime snapshots are explicitly rejected for a separate stream surface, rather than silently loaded as local pages.

The pool keeps one child process per environment/profile and reuses its tabs across thread/tab tuple keys. Showing an existing tab retains its page state. An origin change replaces the existing process before reopening the same partition; two origins never concurrently write that partition. The child receives an environment allowlist with native home/XDG directories, locale and session bus, plus fixed Qt/Chromium settings; backend/provider tokens and arbitrary parent variables are not inherited. ## Import source discovery (source only)

`src/browser_sources.rs` ports the Linux discovery side of original `BrowserImport/Sources.ts` at the pinned revision. The registry retains the original order, names and exact paths for Chrome, Edge, Brave, Vivaldi, Opera, Helium and Firefox; Arc/Safari report unsupportedPlatform on Linux. Discovery requires an actual regular cookie database, preferring Chromium's Network/Cookies over its legacy Cookies file. It honors Local State names/profile order, rejects unsafe Chromium path segments, and falls back to database-bearing directories when metadata is invalid. Firefox ProfileN parsing preserves explicit absolute profile roots and rejects relative traversal; Snap profiles use their absolute directories and deduplicate with the normal installation.
